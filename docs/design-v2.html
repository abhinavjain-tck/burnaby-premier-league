1. Purpose and what changed since v1

v1 picked the stack and sketched the auction. Since then the league agreed the auction rules (ballot in bpl-auction-options.html) and most of the code got written. v2 is the build spec for the last five days: it fixes the data model, the rules engine and the migration path, and nothing else.

Event log: source of truth for the auction

Every console action appends one auction_events row. State is replay(initialState(teams, lots), liveEvents). Undo flags the newest live event and appends an UNDO marker; redo clears the flag and appends REDO. Projections on auction_teams, auction_lots and auctions.status are a cache, rewritten in the same transaction and rebuildable at any time with rebuildProjections().

Payloads carry the result, not just the intent. The console sends a thin command (for example SOLD {lotId}); the server fills in team, amount and the wallet split from the current state and stores that. Replay never re-runs rule checks, so changing a rule later can never rewrite an auction that already happened.

Where the rules run

Inside runCommand's transaction, after the auction row is locked and the log replayed, plan() calls fillAndCheck(state, command, config). That is a pure function in lib/auction/rules.ts: it computes maxBid (squad guard, pool guard, band caps, band-minimum slots, reserve eligibility and lock), fills the ladder amount and wallet split, and throws AuctionRuleError with a plain sentence if the move is not allowed. The console imports the same function to grey out buttons and show the reason. Because the row lock serialises commands for one auction, "check then write" cannot race.

Decisions
  • Bands are rows in season_bands; tier columns stay read-only until after Sunday, then get dropped.
  • seasons.config keeps scalar settings only, with v: 1 and the key list above. Bands never go in jsonb at the season level.
  • auctions.config is a full snapshot including bands, written at creation, editable in draft, frozen at START. format is a column.
  • The console sends thin commands; the server fills amounts and splits. BID amount is always the next ladder step. Custom amounts are removed from the protocol and the UI.
  • Wallets, squad size, band lock and lot status are projections; the event log is the only truth.
  • Owners are pre-placed with PRESOLD from the main wallet and belong to no band.

Auction formats and how the reducer branches

auctions.format picks a reducer and a rule checker. Shared events (START, PAUSE, RESUME, COMPLETE, NOTE, ADJUST_PURSE, PRESOLD, UNDO, REDO) live in one common function; each format adds its own.

type AuctionFormat = "voice_ledger" | "owner_phone_bidding" | "snake_draft";

const formats: Record<AuctionFormat, { apply: Reducer; check: Checker }> = {
  voice_ledger:        { apply: applyVoice,  check: checkVoice },   // S4: operator taps BID/SOLD
  owner_phone_bidding: { apply: applyVoice,  check: checkOwnerBid }, // later: OWNER_BID from owner session
  snake_draft:         { apply: applyDraft,  check: checkDraft },   // later: PICK {lotId, teamId}, no money
};

function apply(s: State, e: Event, format: AuctionFormat): State {
  return isCommon(e) ? applyCommon(s, e) : formats[format].apply(s, e);
}
  • owner_phone_bidding: owners send OWNER_BID {lotId} from their own session; the server fills the ladder amount exactly as for BID, so maxBid is reused unchanged. The clock stays operator-confirmed (the operator taps SOLD when it hits zero), so no background scheduler is needed on Vercel.
  • snake_draft: PICK {lotId, teamId}, pick order derived from team order and round. Wallets are ignored; band caps and the pool guard still apply.
  • The snapshot sent to phones includes format, so every phone runs the same reducer the server ran.

Rosters: team_players.source

  • Trade: in one transaction, set left_at on the old row and insert a new row with source = 'trade'. A small trades(id, season_id, at, registration_id, from_team_id, to_team_id, fee_lakhs, note, approved_by) table records the deal.
  • RTM: needs last season's team_players (exists after this Sunday's publish). Adds events RTM_CLAIM {lotId, teamId} and RTM_FINAL_RAISE {lotId, amount}, and 'rtm' to the roster_source enum.

5. Rules engine spec

All of this lives in lib/auction/rules.ts and reducer.ts. Pure functions, no imports from the server, shared by the console, board, owner view and the transaction.

State the rules read

type Band  = { id: number; label: string; base: number; maxPerTeam: number | null;
               minPerTeam: number; isStar: boolean };
type Team  = { id: string; main: number; reserve: number; reserveBandId: number | null;
               squad: number; bandCount: Record<number, number> };  // players bought per band
type Lot   = { id: string; bandId: number | null; base: number; round: 1 | 2;
               status: "queued" | "on_block" | "sold" | "unsold" | "skipped";
               currentBid?: number; currentTeamId?: string };
type Verdict = { max: number; mainCap: number; reserveOk: boolean; reason: string | null };

maxBid(team, lot, state, config)

const lowestBase = (c: Config) => Math.min(...c.bands.map(b => b.base));   // 2 cr in S4
const have = (t: Team, b: Band) => t.bandCount[b.id] ?? 0;
const inPool = (l: Lot) => l.status === "queued" || l.status === "unsold" || l.status === "skipped";

function maxBid(team: Team, lot: Lot, s: State, c: Config, opts = { poolGuard: c.poolGuard }): Verdict {
  const no = (reason: string): Verdict => ({ max: 0, mainCap: 0, reserveOk: false, reason });
  if (s.status !== "open") return no("Auction is paused");
  if (team.squad >= c.maxSquad) return no(`Squad full (${c.maxSquad})`);
  const band = c.bands.find(b => b.id === lot.bandId);
  if (!band) return no("Lot has no band");

  // 1. Band cap
  if (band.maxPerTeam !== null && have(team, band) >= band.maxPerTeam)
    return no(`Has ${have(team, band)} ${band.label}, max ${band.maxPerTeam}`);

  // 2. Band-minimum slots: after this buy, open slots must still cover every unmet minimum
  const slotsAfter = c.maxSquad - team.squad - 1;
  const owedAfter = c.bands.reduce((n, b) =>
    n + Math.max(0, b.minPerTeam - have(team, b) - (b.id === band.id ? 1 : 0)), 0);
  if (owedAfter > slotsAfter) return no("Open slots are needed for band minimums");

  // 3. Pool guard: every other team can still reach minSquad from what is left
  if (opts.poolGuard) {
    const poolAfter = Object.values(s.lots).filter(l => l.id !== lot.id && inPool(l)).length;
    const othersNeed = Object.values(s.teams).filter(t => t.id !== team.id)
      .reduce((n, t) => n + Math.max(0, c.minSquad - t.squad), 0);
    if (poolAfter < othersNeed) return no(`Would leave another team short of ${c.minSquad}`);
  }

  // 4. Squad guard, on the main wallet: keep lowest base for every slot still needed after this one
  const neededAfter = Math.max(0, c.minSquad - team.squad - 1);
  const mainCap = Math.max(0, team.main - neededAfter * lowestBase(c));

  // 5. Reserve: below this band's minimum, never Star, only the band it is locked to (or none yet)
  const reserveOk = !band.isStar
    && have(team, band) < band.minPerTeam
    && team.reserve > 0
    && (team.reserveBandId === null || team.reserveBandId === band.id);

  return { max: mainCap + (reserveOk ? team.reserve : 0), mainCap, reserveOk, reason: null };
}

// 6. Ladder: the only amount a BID can carry. One step per shout.
function nextBid(lot: Lot, c: Config): number {
  return lot.currentBid === undefined ? lot.base : lot.currentBid + stepAt(c.ladder, lot.currentBid);
}

function bidBlocker(team: Team, lot: Lot, s: State, c: Config): string | null {
  if (s.onBlockLotId !== lot.id) return "That lot is not on the block";
  if (lot.currentTeamId === team.id) return "Already leading";
  const v = maxBid(team, lot, s, c);
  if (v.reason) return v.reason;
  const amount = nextBid(lot, c);
  return amount > v.max ? `Max bid ${fmt(v.max)}` : null;
}

// 7. Paying: main first, down to the squad-guard floor; the rest from reserve.
function split(team: Team, lot: Lot, amount: number, s: State, c: Config, opts?) {
  const v = maxBid(team, lot, s, c, opts);
  if (v.reason) throw new AuctionRuleError(v.reason);
  if (amount > v.max) throw new AuctionRuleError(`Max bid ${fmt(v.max)}`);
  const fromMain = Math.min(amount, v.mainCap);
  const fromReserve = amount - fromMain;            // > 0 only when v.reserveOk
  return { fromMain, fromReserve, reserveBandId: fromReserve > 0 ? lot.bandId : null };
}

Invariants to assert in tests

Checked after every event in the simulation tests (section 10) and, cheaply, after every command in development builds.

  1. Wallets never negative: main >= 0 and reserve >= 0 for every team.
  2. Money adds up: for each team, mainStart - main = sum(fromMain) - sum(main adjustments), and the same for reserve.
  3. Reserve never on Star: no sale with fromReserve > 0 is in a band with isStar.
  4. Reserve on at most one band: the set of band ids across a team's sales with fromReserve > 0 has size 0 or 1, and equals reserveBandId when 1.
  5. Reserve only when short: every sale with fromReserve > 0 happened while the team had fewer than minPerTeam in that band.
  6. Main first: fromReserve > 0 implies fromMain = mainCap at that moment.
  7. Caps hold: squad <= maxSquad, and bandCount[b] <= maxPerTeam(b).
  8. Pool covers needs while open: count(lots in pool or on block) >= sum over teams of max(0, minSquad - squad).
  9. Squad in range at completion: if at START the pool held at least sum over teams of (minSquad - squad) players, every team ends with minSquad <= squad <= maxSquad once placement is done.
  10. Every BID is one ladder step: first bid = base, each next = previous + stepAt(previous).
  11. Replay is deterministic: projections in the DB equal replay(log); undo then redo returns the same state.

Band minimums are not an invariant: a team can end short in a band (the example above). The console and owner view show "short: 1 x 10 cr" so the room sees it.

Decisions
  • Squad guard applies to the main wallet only; reserve sits on top when eligible.
  • Main is drained first down to the squad-guard floor, then reserve. The split is stored in the event.
  • The pool counts queued, unsold and skipped lots. Round-1 unsold players still count because they get a second go.
  • A band-minimum slot guard blocks a buy that would leave too few open slots for unmet band minimums.
  • Placed players cost their base price; the operator may lower it (with a note) only when the chosen team cannot pay.
  • Unused reserve is shown as "lost" after COMPLETE; nothing else happens to it.

10. Testing strategy

Unit: pure rules (Vitest, no DB)

  • Money and ladder (exists): formatting, stepAt at each rung edge (9.5 cr to 10 cr, 49 cr to 50 cr, 97.5 cr to 100 cr).
  • Config: season v0 upgrades to v1; snapshot built from season plus bands; bad values fall back; edits refused after START.
  • Bands: editor validation (min above max, two stars, duplicate code, sum of minimums too high).
  • maxBid table tests, one row per rule: squad guard (100 cr, 6 players, max 92 cr), band cap reached, band-minimum slots, pool guard at exactly 44 players, reserve eligible, reserve on Star refused, reserve locked to another band, reserve shut once the minimum is met, paused auction.
  • Split: main only; main to floor plus reserve; lock set on first reserve use; undo of that sale clears the lock.
  • Reducer: every event type, including PLACE and REQUEUE to round 2; undo and redo of each.
  • Simulation (property-style): 500 seeded auctions (4 teams, 44 to 52 lots, S4 bands). A driver picks random legal commands from bidOptions and the console's allowed actions, including undo, redo, skip, second go and placement, and checks every invariant from section 5 after each step. Uses the existing seeded() PRNG so failures replay by seed.

Postgres integration (commands.db.test.ts, against supabase start)

  • Command writes one event, updates projections and version in one transaction.
  • Same idempotency key twice: one event. Stale expectedVersion: conflict with a fresh snapshot.
  • Two commands fired together with the same version: exactly one wins.
  • 200 random commands, then rebuildProjections: no row changes (projections already equal the replay).
  • Check constraint: a hand-crafted negative wallet update fails.
  • publishRosters: correct rows, sources and prices; second call adds nothing; test auction refused; commands refused afterwards.
  • Migrations: on a DB seeded with M/A/B/C tiers and wicket_keeper rows, 1b and 2 to 3 produce the right bands and keeper flags; migration 4 refuses when a live auction has started.

12. Open questions

Only the ones that change code or the rules sheet. Each has the answer this doc assumes.

Q1
Does the owner count toward a band's cap or minimum?
Assumed: no. The owner counts toward squad size (11 to 13) only.
Q2
Should band minimums also block buys that would leave too few open slots (the band-minimum slot guard)?
Assumed: yes. Without it, minimums only affect when the reserve opens. Rarely triggers with 13 slots and minimums summing to 5.
Q3
When a bid goes past the main wallet, does main drain to zero or only to the squad-guard floor?
Assumed: to the floor, so the team can still fill its squad at 2 cr each. Draining to zero could leave a team unable to reach 11.
Q4
What does a placed leftover cost, and can the reserve pay for it?
Assumed: base price, paid like a sale (reserve if eligible). If the team cannot pay base, the operator lowers it with a note.
Q5
Who is the operator, who is the backup, and what are their Google emails?
Needed by Friday for auction_admins.
Q6
If a band's pool is smaller than 4 x its minimum on Saturday, do we re-band players or lower the minimum?
Assumed: the organiser re-bands before START; the setup check blocks until it adds up.
Q7
Is Saturday noon still the edit lock and registration close?
Assumed: yes, set in edits_lock_at.
