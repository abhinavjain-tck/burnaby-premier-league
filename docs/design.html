Mongo vs Postgres, specifically

The data is relational at its core: a player registers for a season, a lot puts a player in an auction, a bid links a lot to a team, a sale moves purse from a team. Undo means reversing exactly one of those links. Postgres gives foreign keys, a unique constraint on "one sold row per lot", a check that purse never goes negative, and a single transaction around "record sale + append event + bump version". Mongo can do all of that, but each guarantee is code instead of schema. For a hundred users the performance difference is zero, so the decision is about which one catches our mistakes at 9 pm on auction night. Postgres does.

The one place Mongo would have been nicer is player profile fields that vary (some players add a video, some add three stats). A jsonb column covers that.

Why not a Turborepo

One Next.js app with route groups: (public), (player), (admin), (auction). Shared components live in components/. A monorepo adds build config and a second package.json for a team of one or two. If a separate "projector" app ever needs its own deploy, it can be a second Vercel project pointing at a subfolder later.

Vercel Hobby fine print

Hobby is licensed for personal, non-commercial use. A volunteer community league showing sponsor logos is a grey area. Options: accept it, or pay for Pro (US$20/month) for the auction month only. Hobby also caps a function at 60 seconds and gives ~100 GB bandwidth a month, both fine for us. The realtime constraint above is the one that shapes the design.

Architecture

Two boxes. Vercel renders pages and runs the server actions. Supabase holds everything that persists and fans out realtime. Browsers talk to Supabase directly only for two things: uploading an image and subscribing to the auction channel.

Rendering strategy

  • Public pages (landing, news, sponsors, team pages): RSC, statically cached, revalidated by tag when an admin saves. Fast on a 3G phone in a park.
  • Player and admin pages: RSC per request, read with the user's session so RLS applies.
  • Auction pages: RSC renders the current snapshot, then a small client component subscribes to the channel and patches state. First paint shows real data even if the socket takes a second.
  • Writes: Server Actions everywhere. Each action re-checks the role server-side. No client ever holds a service key.

Auth: one door, several keys

Season 4 cut

Players do not log in. The registration form is public. On submit we create the row and show a private URL /r/<edit_token>, also sent to the player's WhatsApp by the admin or copied by the player. That link edits the card until the pool locks. Cost: if a player loses the link, an admin resends it from the registrations table. Saving: a full day of auth UI, and zero "I can't sign in" messages on Sunday.

Admins, the auctioneer and the 4 owners sign in with Google. Their emails are an allowlist in user_roles. That is about eight accounts in total. Everything below about roles still applies; the player login path is simply built after the auction.

When player login does arrive: separate player and admin logins sound tidy but double the screens, the password resets, and the "which one do I use" questions in the WhatsApp group. One Supabase Auth login, roles in a table.

Recommended: Google + magic link

Most players have Gmail on their phone; Google sign-in is one tap. Magic link covers everyone else and needs no password. Admins are the same accounts with a row in user_roles.

Alternative: username + password

Works offline from Google, but we own reset flows and weak passwords. Only worth it if several players refuse Google and cannot receive email.

Alternative: phone OTP

Cricketers know their phone number better than their email. Supabase supports it, but SMS costs money (Twilio). Park it for season 5.

How roles get assigned

  1. Super admin emails are seeded in an env var, so the first login works without a UI.
  2. Super admin adds an admin by email in /admin/people. A row is written to user_roles even before that person signs in; it attaches on first login by email match.
  3. Owner is not a global role. It is a row in team_owners(team_id, user_id), scoped to a season.
  4. Auction admin is a row in auction_admins(auction_id, user_id), so a test auction can have a different operator.

Session lives in an httpOnly cookie via @supabase/ssr. Middleware refreshes it. RLS policies use auth.uid() and a small is_admin() SQL function so the same rule protects direct Supabase calls and server actions.

Data model

Everything hangs off seasons. The auction tables are separate from the roster tables on purpose: a test auction must never write to a real team.

Key tables

create type reg_status as enum ('interested','registered','confirmed','withdrawn');
create type player_role as enum ('batter','bowler','all_rounder','wicket_keeper');
create type lot_status  as enum ('queued','on_block','sold','unsold','skipped');
create type auction_status as enum ('draft','open','paused','completed');

create table seasons (
  id smallserial primary key, name text not null, year int not null,
  status text not null default 'upcoming',     -- upcoming|registration|auction|live|done
  purse int not null default 10000,
  config jsonb not null default '{}'            -- tiers, increments, min/max squad
);

create table player_registrations (
  id uuid primary key default gen_random_uuid(),
  season_id smallint references seasons not null,
  user_id uuid references auth.users not null,
  status reg_status not null default 'interested',
  role player_role, batting_style text, bowling_style text,
  tier char(1) check (tier in ('M','A','B','C')),
  bio text check (char_length(bio) <= 280),
  stats jsonb not null default '{}',            -- {matches, runs, wickets, best}
  paid_at timestamptz, paid_marked_by uuid, payment_proof_url text,
  created_at timestamptz default now(),
  unique (season_id, user_id)
);

create table auction_events (
  id bigserial primary key,
  auction_id uuid references auctions not null,
  seq int not null,                             -- 1..n per auction, gap-free
  type text not null,                           -- START_LOT|BID|SOLD|UNSOLD|SKIP|ADJUST_PURSE|PAUSE|RESUME|REORDER
  payload jsonb not null,                       -- {lot_id, team_id, amount, note}
  undone boolean not null default false,        -- set by UNDO, cleared by REDO
  actor uuid not null, at timestamptz default now(),
  unique (auction_id, seq)
);

Storage: ~100 registrations, ~110 lots, maybe 1,500 bid events, a few hundred posts. Under 5 MB of Postgres for the season. Photos at 200 KB × 120 people ≈ 25 MB. The 500 MB and 1 GB free limits are not a concern for years.

Details that matter

  • Photo upload: browser resizes to 1024 px longest side, WebP, ~150 to 250 KB, using browser-image-compression. Uploads straight to Supabase Storage with a signed upload URL from a server action. Server stores the path, never the file.
  • CricHeroes link: validate that it matches cricheroes.com/player-profile/<id>/… and store the numeric id. Phase 3: a nightly job fetches the public profile page and caches the headline numbers. There is no official API, so treat that as best effort and keep the self-reported fields.
  • Interested vs registered: with no login, "interested" collapses into the form itself: step 2 alone (name, number, role) submits and creates a registered row; the card fields are optional and editable later through the edit link. Admin ticking payment flips to confirmed. Admin can also mark withdrawn.
  • Editing: the edit link works until the admin locks the pool (proposed Saturday noon, so tiers and sets can be set). After that only admins edit. Duplicate guard: same phone number twice shows "already registered, resend my link".
  • Admin registration table: sortable, filter by status and role, tap a row to tick paid, bulk export CSV. Role and tier counts at the top so you can see if you have six wicketkeepers and no spinners.
  • Confirmation: the done screen and a "copy my edit link" button. No email in v1; the admin table has a "copy WhatsApp message" button per row that includes the link.

The auction

This is the part people will remember. It has to be fair, legible from the back of a hall, and recoverable when the auctioneer taps the wrong team.

How the IPL does it

Worth copying because everyone in the room already understands it.

  • Purse: fixed per team. Retentions come off the purse before the auction.
  • Base price: each player picks from a small set of tiers. Bidding starts at base.
  • Sets: players are grouped into sets by role (batters, all-rounders, keepers, pace, spin), with a marquee set of the biggest names first to set the market. Order within a set is drawn randomly.
  • Increment ladder: the minimum raise grows with the price (e.g. 5 lakh steps below 1 crore, 10 lakh to 2 crore, 20 lakh to 5 crore, 25 lakh beyond).
  • Squad guard: a team cannot bid more than purse − (min squad size − current squad − 1) × lowest base price, so everyone can still fill their squad.
  • Right to Match: a team can match the winning bid for a player it had last season; the winning bidder then gets one final raise.
  • Accelerated round: after the marquee and first sets, teams nominate unsold or unauctioned players to bring back, run quickly at base price.
  • Unsold: no bid at base means unsold; they can return in the accelerated round.

Format options for BPL

1 · Voice auction, app as ledger Sunday

Auctioneer calls the bids by voice on the ground. One operator records each bid on a phone. Every other phone is the board. Lowest tech risk, highest atmosphere. The app cannot get the auction wrong on its own; only the operator can, and undo fixes that.

2 · Owners bid on their phones

Each owner taps Bid +50. Server serialises bids, a 10 s clock resets on each bid, auto-sold when it expires. Works fully remote. Risk: one owner on bad Wi-Fi ruins the room, and disputes shift from "he said 500" to "my tap didn't register". Not for Sunday: five days is not enough to build and rehearse it, and a ground with fifty phones on one tower is the worst place to debut it. The event model supports it, so it is a Season 5 upgrade.

3 · Snake draft

No money. Teams pick in order 1→8, 8→1. Fast, dead simple, fair by construction. Good fallback if the auction rules cannot be agreed by auction day. The lot and event tables support it with PICK events.

4 · Sealed bids

Every team submits a secret bid per player; highest wins. Quiet, no drama, and nobody knows the market. Not recommended; mentioned so it is consciously rejected.

Increment ladder

The console shows exactly two buttons per team: "+step" and "custom". Custom must be a multiple of the step. Jumping 10 cr → 30 cr is allowed; 10 cr → 10.3 cr is not. With only 4 teams, the four "+step" buttons fit in one row of a phone screen in team colours.

Ground-specific design

  • Sunlight: the public board uses a white background, near-black type, and team colours as thick bars, not tints. Current bid is the largest thing on screen.
  • Cellular: fifty phones on one tower. Board payloads are tiny (one event per broadcast). If the socket drops, the client polls a 2 KB snapshot every 5 seconds. The console retries a failed action with the same idempotency key so a double-tap never records two bids.
  • Battery: no video, no animation loops, dark type on white. The console phone should be on a battery pack.
  • Noise: the auctioneer needs a speaker. The app cannot fix that, but the visible countdown and the big "SOLD" flash help people at the back.
  • Two phones for the auction team: auctioneer calls and watches the board; an operator taps the console. If it is one person, the console has a "board" tab so they can flip.
  • Backup ledger: one person keeps a paper list of sold players and prices. The CSV export at each break is the digital backup.

State machine

Undo and redo: event sourcing, small version

Every button on the console appends one row to auction_events inside a transaction that also updates the projection tables and increments auctions.version. Undo does not delete; it flags the most recent non-undone event as undone = true and re-applies the projection from the last snapshot. Redo clears the flag on the most recent undone event, if no new event has landed since.

-- Rebuild any auction's state from scratch (also the test for the projection code):
select type, payload from auction_events
 where auction_id = $1 and not undone
 order by seq;

-- Reducer (TypeScript, pure, ~120 lines):
state = events.reduce(apply, initialState(auctionTeams, auctionLots))
// apply(state, {type:'SOLD', payload:{lot_id, team_id, amount}}) =>
//   team.purse_left -= amount; team.slots_left -= 1; lot.status='sold'; lot.sold_to=team_id; lot.price=amount
  • Why not just an "undo last sale" button? Because the mistake is discovered three lots later. With the log, the admin opens the event list, sees "Lot 41 SOLD to Strikers 650", and can undo that specific event with a REVERSE(seq) event that appends a compensating action. Ordinary undo is the fast path; targeted reverse is the safety net.
  • Adjust purse: ADJUST_PURSE {team_id, delta, note}. Used for penalties, manual corrections, or a late owner buy-in. Shows on the board with the note, so it is never a quiet edit.
  • Concurrency: two operators on the console at once is the real risk. Each action carries the version the client saw; the server rejects it if the DB is ahead ("Board changed, refresh"). Postgres select … for update on the auction row makes this exact.
  • Export: one button dumps the event log and final rosters as CSV. Post it in the WhatsApp group after the auction. Total transparency costs nothing.

Test auctions and the private link

  • An auction has mode = test | live. Only one live auction per season. Test auctions are unlimited.
  • Test auctions can be seeded three ways: random fake players (generated names, roles, tiers), the real registered pool (read-only copy of registrations), or a CSV.
  • Test auctions never appear in navigation. They are reached by /auction/t/<share_token>, a 20-char random token. Anyone with the link can watch; only assigned auction admins can operate.
  • Completing a test auction never publishes rosters. The button is not rendered for test mode and the server refuses it.
  • Admin can "promote" a test's configuration (sets, order, tiers) to the live auction with one click, so the rehearsal and the real thing run the same script.

Pre-auction page

Public at /auction from the day registration closes. Countdown to start time, the rules page rendered from markdown, the eight teams and owners, the full pool grouped by set with tiers and base prices, and the sponsor line-up. When the live auction opens, the same URL becomes the public board. No second link to share.

Realtime and notifications

Only the auction needs true realtime. Everything else is fine with a page refresh.

  • Channel: auction:{id} via Supabase Realtime Broadcast. Server action publishes {version, event} after the transaction commits. Clients apply the event with the same reducer used server-side; if version skips, they fetch a snapshot. Realtime is a hint, Postgres is the truth.
  • Why Broadcast and not Postgres Changes: Changes would push raw row diffs from several tables, and RLS on realtime is fiddly. Broadcast sends one tidy event we control.
  • Persistence: events are already persisted. A separate notifications table exists only for personal ones: "you were sold", "payment confirmed". These render as an in-app inbox with an unread badge.
  • Push notifications: Web Push with VAPID keys works on iOS 16.4+ when the site is added to the home screen, free, no vendor. Phase 3. Until then the WhatsApp group does what it does today.
  • Capacity: 200 concurrent connections on the free tier vs ~60 phones on the ground. Plenty. The public board still falls back to polling every 5 s if a socket drops, which on cellular it will.
  • Reconnect: on visibilitychange (phone unlocked) the client refetches the snapshot. Phones sleep constantly in a hall; this one line avoids most "my screen is stuck" complaints.

Security and privacy

  • RLS on every table. Players read and write only their own registration. Admin functions checked via is_admin(). Auction event inserts allowed only for auction_admins of that auction. Public tables (sponsors, posts, teams, published rosters) readable by anon.
  • Phone numbers and payment status never leave the server; public and owner views select from a view that excludes them.
  • Payment screenshots go in a private bucket, served through signed URLs that expire in 10 minutes, admin only.
  • Service role key exists only in Vercel env vars and is used only by the cron and the publish step. Server actions run as the user.
  • Test auction tokens are unguessable but not secret-secret: treat them as "unlisted YouTube". Rotate with one click.
  • Uploads capped at 5 MB pre-compression, image types only, filenames replaced with UUIDs.
  • Backups: Supabase free has no point-in-time recovery. A daily GitHub Action runs pg_dump to a private repo. On auction day, the event log export is the backup.
  • Privacy: a one-paragraph notice at registration about what is public (name, photo, role, stats, team) and what is not (phone, email, payment). Players can withdraw and request deletion; admin button anonymises the row.

Risks and what we do about them

RiskLikelihoodMitigation
Cellular is bad on the groundhighConsole actions retry with an idempotency key. Board degrades to 5 s polling. One person keeps a paper ledger. Event log export at every break. Know which corner of the ground has signal before Sunday.
Operator taps wrong teamhighUndo button, confirm dialog on SOLD showing team colour and amount in big type, 2 s "cancel" toast before broadcast.
Supabase free project pauses after 7 idle daysmediumVercel cron pings a keep-alive route daily. Also check the dashboard the morning of the auction.
Vercel Hobby commercial clauselowUpgrade to Pro for one month if asked; the app changes nothing.
Players do not finish registration on phonemediumStep 2 alone registers them; the rest is optional. Admin can fill a card in for someone over the phone.
Player loses their edit linkmediumAdmin resends from the table. Phone-number match on the form offers "resend my link".
Rule disputes mid-auctionmediumRules page public two weeks ahead, rehearsal with owners, every ruling logged as a NOTE event, auction admin has final say.
Data losslowNightly pg_dump to GitHub; CSV export button; Postgres is the single source of truth.
Five days is not enoughmediumRegistration and admin ship first regardless. If Thursday slips, Sunday runs on the console alone with polling and no owner view; the board still works. If Friday slips, the paper ledger is the auction and the app records results afterwards.
Single developer gets sick the week of launchlowEverything is in the repo with a README; a co-organiser has Vercel and Supabase access via the league account.
